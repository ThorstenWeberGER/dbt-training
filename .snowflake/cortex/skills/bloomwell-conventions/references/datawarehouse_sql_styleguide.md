## 1. Medallion Architecture Overview

Our data warehouse is organized in layers. Each layer has a distinct responsibility and lives in its own schema. The schema name communicates the layer — table names never repeat this.

```
Source Systems
     │
     ▼
┌─────────────┐
│   BRONZE    │  Raw ingestion — as-is from source
└──────┬──────┘
       │
       ▼
┌─────────────┐
│   STAGING   │  Casting, renaming, deduplication (views only)
└──────┬──────┘
       │
       ▼
┌─────────────┐
│   SILVER    │  Conformed star schemas — enterprise view
└──────┬──────┘
       │
       ▼
┌─────────────┐
│    GOLD     │  Aggregated marts, data products, external sharing
└─────────────┘
```

> **TESTING** schemas exist as a playground — views only, never production data.

## 2. Schema Organization

| Layer | Schema Pattern | Purpose | Example |
|---|---|---|---|
| **Bronze** | `BRONZE.{source_system}` | Raw data from source systems | `BRONZE.HUBSPOT` |
| **Staging** | `STAGING.{purpose}` *(views only)* | Casting, renaming, deduplication | `STAGING.HUBSPOT_PREP` |
| **Silver** | `SILVER.{subject_area}` | Conformed star schemas, enterprise view | `SILVER.APPOINTMENTS` |
| **Gold** | `GOLD.{use_case}` | Aggregated marts, data products | `GOLD.FINANCE_REPORTING` |
| **Playground** | `TESTING.*` *(views only)* | Development and testing | `TESTING.dev_thorsten` |

**Schema naming examples by layer:**

- **Bronze** → `BRONZE.HUBSPOT`, `BRONZE.XPERTYME`, `BRONZE.SHOPIFY`
- **Silver** → `SILVER.APPOINTMENTS`, `SILVER.MEDICATIONS`, `SILVER.PHARMACY`
- **Gold** → `GOLD.SUPPLIER_ANALYTICS`, `GOLD.FINANCE_REPORTING`

> ⚠️ **Open question (TW):** Is Staging strictly after Bronze, or can it also handle raw file imports from CSV/Excel? Clarify and update this table accordingly.

## 3. Table Naming Conventions

### 3.1 Prefixes by Layer

| Layer | Prefix | Example |
|---|---|---|
| **Bronze** | *(none — schema provides context)* | `BRONZE.HUBSPOT.contacts` |
| **Staging** | `{source}__{entity}` *(double underscore)* | `hubspot__contacts` |
| **Silver — Dimensions** | `dim_` | `dim_patient` |
| **Silver — Facts** | `fct_` | `fct_prescription` |
| **Silver — Bridge** | `bridge_` | `bridge_patient_diagnosis` |
| **Gold — Marts** | `mrt_` | `mrt_monthly_prescription_volume` |

> **Note on Bronze:** A `brz_` prefix is under consideration for consistency with other layers. Decide as a team and update this guide.

### 3.2 Naming Rules

**Staging models** use `{source}__{entity}` with a double underscore separating source from entity:
```
hubspot__contacts
xpertyme__appointments
```

**Dimension tables** use `dim_` prefix. Use singular unless the grain is genuinely plural:
```
✅  dim_patient       (one row per patient)
❌  dim_patients
```

**Fact tables** are always singular — they describe an event:
```
✅  fct_prescription
✅  fct_appointment
❌  fct_prescriptions
```

**Bridge tables** for many-to-many relationships use `bridge_`:
```
bridge_patient_diagnosis
```

**Do not encode the SCD type in the table name.** Document the SCD strategy in dbt model metadata instead:
```
✅  dim_patient         → document SCD2 in YAML
❌  dim_patient_scd2
```

**Use `snake_case` everywhere.** No camelCase, no PascalCase.

### 3.3 Staging Materialization

Staging models must be materialized as **views** or set to **ephemeral** in dbt. They are transformation steps, not storage layers. Persisting as tables requires explicit justification documented in the model config.

## 4. Column Naming Conventions

### 4.1 Key Columns

| Key Type | Convention | Example |
|---|---|---|
| Surrogate key (PK / FK) | `{entity}_key` | `patient_key`, `pharmacy_key` |
| Business key (from source) | `{entity}_id` | `patient_id`, `hubspot_contact_id` |
| Composite business key | `{entity}_{qualifier}_id` | `appointment_external_id` |

> **Rule:** `_key` → surrogate integer generated by our pipeline. `_id` → business identifier from a source system. These suffixes are never interchangeable.

### 4.2 Data Type Suffixes

| Type | Suffix | Example |
|---|---|---|
| Timestamp (with time) | `_at` | `created_at`, `cancelled_at` |
| Date (no time) | `_date` | `birth_date`, `prescription_date` |
| Boolean | `is_` or `has_` prefix | `is_active`, `has_prescription`, `is_deleted` |
| Monetary amount (in cents) | `_amount` | `service_amount`, `refund_amount` |
| Count / quantity | `_count` or `_quantity` | `appointment_count`, `prescribed_quantity` |
| Percentage / ratio | `_pct` or `_ratio` | `churn_pct`, `fill_ratio` |
| Duration | `_duration_{unit}` | `call_duration_seconds`, `wait_duration_minutes` |
| Free text / comments | `_text` or `_note` | `cancellation_note`, `diagnosis_text` |
| CET date or timestamp *(Gold only)* | `_cet` postfix | `service_date_cet`, `shipping_date_cet` |

### 4.3 General Column Rules

- **Use full words.** `patient_key`, not `pat_key`. `prescription_date`, not `rx_dt`.
- **Avoid SQL reserved keywords** as column names (`date`, `order`, `status`). Prefix them: `appointment_date`, `service_order`, `patient_status`.
- **Boolean columns must be answerable with yes/no.** `is_active` reads as "is active? yes/no."
- **Avoid `type` as a standalone column name.** Use `appointment_type`, `service_type`, etc.
- **Bronze keeps source column names as-is.** Renaming to match these conventions happens in staging models.

## 5. Grain Documentation

Every fact table **must** document its grain. This goes in the model's YAML description in dbt.

### Format

```yaml
models:
  - name: fct_prescription
    description: >
      One row per prescription issued. Grain: one prescription event
      per patient per doctor per prescription_date.
    columns:
      - name: prescription_key
        description: Surrogate key for the prescription fact.
        tests:
          - unique
          - not_null
```

> 💡 **Grain test:** If you cannot state the grain in one sentence, the model likely has a grain problem. Fix the model — not the description.

## 6. Snowflake Constraints

We add `PRIMARY KEY` and `FOREIGN KEY` constraints to all **Silver** and **Gold** tables. These are **metadata-only** — Snowflake does not enforce them.

### Why we add them

1. Document relationships in Snowflake metadata
2. Enable automated ER diagram generation from DDL
3. Allow Cortex AI to understand join paths when generating SQL

### Enforcement via dbt tests

| What to validate | dbt test |
|---|---|
| Primary key uniqueness | `unique` + `not_null` on the `_key` column |
| Foreign key validity | `relationships` test referencing the parent dimension |
| Not null | `not_null` on required columns |

> ⚠️ **Both the constraint AND the corresponding dbt test are required.**
> The constraint without the test is decoration. The test without the constraint misses the metadata benefit.

### Adding constraints in dbt

```sql
-- In dbt model config or post-hook
ALTER TABLE {{ this }} ADD PRIMARY KEY (prescription_key);
ALTER TABLE {{ this }} ADD FOREIGN KEY (patient_key)
  REFERENCES {{ ref('dim_patient') }} (patient_key);
```

## 7. Role-Playing Dimensions

When a single dimension appears multiple times in a fact table, use **descriptive foreign key names** — never create separate copies of the dimension.

**Example — `dim_date` used three times in `fct_prescription`:**

```yaml
fct_prescription:
  - prescription_date_key   →  dim_date.date_key
  - created_date_key        →  dim_date.date_key
  - dispensed_date_key      →  dim_date.date_key
```

The dimension is one table. The foreign key names in the fact table differentiate the roles.

---

## 8. Conformed Dimensions

Dimensions shared across multiple fact tables must be **identical**. `dim_patient` used by `fct_prescription` and `fct_appointment` is the **same table**, not two separate versions.

If a Gold mart needs a subset of a dimension, it references the Silver dimension or creates a view — it does **not** create a new `dim_patient_lite` in Gold.

> This is non-negotiable. Conformed dimensions are what make cross-domain analysis possible.

## 9. dbt Documentation Requirements

| Layer | Model description required | Column descriptions required |
|---|---|---|
| **Bronze** | Optional (use AI assist) | Optional (use AI assist) |
| **Staging** | Optional (use AI assist) | Optional (use AI assist) |
| **Silver** | ✅ Yes — including grain statement | ✅ Yes — all columns |
| **Gold** | ✅ Yes — including intended consumer/use case | ✅ Yes — all columns |

> **CI enforcement:** The CI pipeline will fail if a Silver or Gold model is missing its model description or has undocumented columns.

### Persisting documentation to Snowflake

Add the following to `dbt_project.yml` to materialize descriptions as Snowflake column/table comments:

```yaml
models:
  bloomwell:
    +persist_docs:
      relation: true
      columns: true
```

## 10. Naming Don'ts

| ❌ Don't | ✅ Do instead |
|---|---|
| Prefix with layer names when the schema already communicates this | `BRONZE.HUBSPOT.contacts` not `BRONZE.HUBSPOT.brz_hubspot_contacts` |
| Use non-universal abbreviations | `appointment` not `appt`, `pharmacy` not `pharm` |
| Encode data types in names | `patient_name` not `patient_name_varchar` |
| Use generic names | `appointment_status` not `status` |
| Add version numbers | Replace the model — don't add `_v2` |
| Use `type` as a standalone column | `appointment_type` not `type` |
| Encode SCD strategy in table names | `dim_patient` not `dim_patient_scd2` |
