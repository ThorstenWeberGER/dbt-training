<RichText id="intro">

This project puts three SCD2 implementations side by side and runs the same four Bronze edge cases through each one. The data source is an invoices-baskets Bronze log — append-only, with duplicates and out-of-order rows that arrive in hourly batches. All three implementations run against a local DuckDB file (`scd2_demo.duckdb`). A `current_batch` dbt variable simulates hourly loads arriving one batch at a time.

The three implementations are:
- **snap_invoices_ts** — native dbt snapshot, `strategy='timestamp'`
- **snap_invoices_check** — native dbt snapshot, `strategy='check'` on `basket_id` + `is_active`
- **scd2_invoices** — custom incremental model using `LEAD()` window functions over an append-only Bronze log

</RichText>

<RichText id="batch-h">

### How the Batch Simulation Works

</RichText>

<RichText id="batch-explainer">

All 3 batch CSVs are loaded by `dbt seed` upfront. To make the models see them one at a time, `stg_bronze_invoices` filters to `batch_id <= current_batch`. The run script rebuilds this model at the start of each simulated run with an increasing var:

```bash
dbt run --select stg_bronze_invoices --vars '{"current_batch": 1}'   # Run 1: 3 rows
dbt run --select stg_bronze_invoices --vars '{"current_batch": 2}'   # Run 2: 8 rows
dbt run --select stg_bronze_invoices --vars '{"current_batch": 3}'   # Run 3: 10 rows
```

`stg_snapshot_input` uses `batch_id = current_batch` (exact match) — it shows **only the new rows arriving in this run**, which is what the snapshots should see. `scd2_invoices` reads `stg_bronze_invoices` directly (the full growing log) and uses `batch_id > MAX(batch_id) FROM this` as its incremental watermark.

**Why this matters:** without the `batch_id <= current_batch` filter in `stg_bronze_invoices`, `scd2_invoices` would see all 10 rows on its first full-refresh run and immediately produce the final 7-row output. Runs 2 and 3 would find nothing new (`batch_id > 3 = empty`). The filter makes each run incremental and realistic.

</RichText>

### snap_invoices_ts — Native Snapshot (timestamp strategy)

</RichText>

<RichText id="ts-explainer">

The timestamp strategy tracks changes by comparing the source `updated_at` column against the stored `dbt_updated_at`. If `source.updated_at > dbt_updated_at`, dbt closes the current open row and inserts a new one. `dbt_updated_at` stores the **source application timestamp** — making it reliable for point-in-time queries.

</RichText>

### snap_invoices_check — Native Snapshot (check strategy)

</RichText>

<RichText id="check-explainer">

The check strategy compares column values directly instead of relying on a timestamp. Change is detected when the hash of `check_cols` (here: `basket_id` + `is_active`) differs between the current source row and the stored row. This means it can detect changes even without an `updated_at` column — but at a cost: `dbt_updated_at` is set to `current_timestamp()` at run time, not to the source application time.

</RichText>

### scd2_invoices — LEAD()-based Incremental Model

</RichText>

<RichText id="scd2-explainer">

This model reads from the append-only Bronze log (`stg_bronze_invoices`) directly. Each incremental run finds rows with `batch_id > MAX(batch_id)` from the previous run, deduplicates exact duplicates, computes `valid_to` using `LEAD()`, and merges the results. Two guards prevent edge case failures: a `valid_from > existing.valid_from` check to prevent zero-width intervals on re-delivered duplicates (EC1/EC3), and a `scd_id NOT IN rows_to_close` filter to prevent duplicate merge keys when a cross-run duplicate arrives alongside a real successor in the same batch (EC3).

</RichText>

<RichText id="findings-h">

### Key Findings

</RichText>

<Callout id="finding-ec2" tone="warning">

**EC2 (two rows for the same invoice_id ±1s in one batch) breaks both native snapshot strategies on DuckDB.**

Both rows trigger `row_changed=true` but the snapshot's MERGE is keyed on `unique_key` (`invoice_id`). DuckDB processes both rows and produces two open rows for INV-002 — the snapshot invariant (one open row per unique_key) is broken. On Snowflake, the same situation raises `ERROR_ON_NONDETERMINISTIC_MERGE` instead of silently corrupting the data.

The LEAD()-based model handles this correctly because it operates on the append-only Bronze log. `LEAD()` computes `valid_to` for each row independently — BKT-B/false gets `valid_to = 10:30:01` (when BKT-D arrived), and BKT-D/true gets `valid_to = NULL` (still open). The full three-step transition is preserved.

</Callout>

<Callout id="finding-dbt-updated-at" tone="info">

**`dbt_updated_at` means different things depending on the snapshot strategy.**

With `strategy='timestamp'`, `dbt_updated_at` stores the **source `updated_at` column value** — application time. A query like "what basket was active for INV-003 on Jan 15 at 10:00?" is answerable and correct.

With `strategy='check'`, `dbt_updated_at` is set to **`current_timestamp()` at the moment dbt ran** — system time. The column only tells you when dbt processed the change, not when it happened in the source system. Point-in-time queries are unreliable. In the test output, `dbt_valid_from` for Run 1 rows shows `2026-06-24 09:30:…` (today's clock), not `2024-01-15 09:00:00` (source time).

</Callout>

<Callout id="finding-batch-design" tone="info">

**The batch simulation required a non-obvious design choice in `stg_bronze_invoices`.**

All three batch CSVs are loaded by `dbt seed` upfront — there's no way to partially load seeds in dbt. Without the `WHERE batch_id <= current_batch` filter, `scd2_invoices` would see all 10 rows on its first full-refresh run and produce the entire 7-row final output immediately. Runs 2 and 3 would then find no new data (`batch_id > 3 = empty`).

The fix: `stg_bronze_invoices` is rebuilt at the start of each simulated run with the appropriate `current_batch` var. This makes it behave as a growing table — 3 rows after Run 1, 8 rows after Run 2, 10 rows after Run 3 — which is what `scd2_invoices` needs for its `batch_id > MAX(batch_id)` watermark logic to work correctly.

</Callout>
